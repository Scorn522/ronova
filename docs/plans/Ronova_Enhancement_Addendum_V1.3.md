## 1. 为什么是这九条

现有能力发布的**全局生产者只有一个**，产出**恰好 6 个键**：

`src/main/java/dev/ronova/coremod/policy/RuntimeCapabilityProjection.java:9-25`
→ `PROTECT_CODE_INTEGRITY`、`RUNTIME_CRITICAL_CLASS_WATCH`、`INTERCEPT_INSTRUMENTATION`（来自 `code` 证明）
→ `RUNTIME_JVMTI`、`RUNTIME_NATIVE`、`RUNTIME_BACKGROUND_INTEGRITY`（来自 `enforcement` 证明）

而 `StrengthOptionKey` 有 **54 个键**（`StrengthOptionKey.java:8-64`，分面 15 ATTACK / 10 INTERCEPTION / 17 PROTECTION / 12 RUNTIME）。

**剩下 48 个键没有全局生产者。** 但请注意——这**不等于**"48 个功能不可达"：`RecoveryChainPolicy` 有 4 条本地通道（`:75`/`:94`/`:107`/`:110`），`TerminalActionPolicy` 有本地作用域的 `withCapability`（`:40-43`），它们是**故意不发布**的（`RecoveryChainPolicy.java:93` 注释、`TerminalActionPolicy.java:35-36` 注释都写明了这一点）。

所以真正的缺口不是"48 个键没接线"，而是——

> **全局能力发布 / 本地执行 / 诊断三者之间没有连起来。**

**V1.3 的九条方向，全部是在这个缺口上做增量，而不是去把 48 个键逐个"点亮"。**

### 方向 ①｜观测成本模型（**前置项**，建议最先做）

**定义：** 给"观测"这个动作建立**按（表面 × 事件源）计价**的成本模型，使每一条新增的原生事件源在上线前就先有一行预算账。

**现状证据：**

- `src/main/java/dev/ronova/coremod/budget/BudgetCategory.java:5-10` — 恰好 6 个类别，且**只有类别维度**：
  `TERMINAL(500µs,256)`、`CAPABILITY(400,64)`、`DISCOVERY(300,MAX)`、`ADMISSION(400,128)`、`OBSERVATION(200,256)`、`MAINTENANCE(200,64)`
- 全 `budget` 包内 `CrossSurface|crossSurface` 命中数 = **0**
- 预算**没有"表面"维度，也没有"事件源"维度**（8 个 `RuntimeSurface` 已定义，但没有进入预算键）

**缺口：** 现在无法回答两个必须回答的问题：

1. "在 NETWORK 表面上开 `OBSERVATION` 要花多少"——答不出，因为 OBSERVATION 是一个池子，不是一组按表面归集的账。
2. "再加一个原生事件源放不放得下"——答不出，因为新事件源的边际成本没有计价单位。

**这一点是 ② 和 ③ 的硬前置。** ②③ 都要新增原生回调，而回调是**最贵**的观测形式（每次事件的本地转换 + 是否 safepoint-safe 的差别）。没有成本模型就上回调，等于在没有账本的情况下加杠杆。

**提议：**

1. 保留现有 6 个类别作为**一级维度**不动。
2. 给 `OBSERVATION`（必要时含 `MAINTENANCE`）增加**二级归集键**：`(RuntimeSurface, 事件源标识)`。
3. 每个新增原生事件源在提案里必须自带一行：触发频率上界、单次本地成本、是否可重入、是否在 safepoint 内、超预算时的降级动作。
4. 超预算动作必须**显式三选一**并写进契约：丢弃观测 / 降采样 / 关闭该事件源。不允许"静默继续观测"。

**前置依赖：** 无。这是根。

**规则检查：** L0 — 不涉及。UX1 — 不涉及。P 层 — 新增内部记账维度，不改外部契约编号，自洽。

**验收标准（可观测、可反驳）：**

- 给定任意一个已注册事件源，能查出一行 `(surface, source, 上界频率, 单次成本, 降级动作)`。
- 人为把某事件源频率拉过其声明的上界，**能观测到**声明的降级动作发生，且有一份计数证据。
- 新增一个事件源但**不给成本行**时，构建/自检**失败**（而不是默认放行）。

**过度声称风险：**

- 不得写成"已实现全局资源调度"。本文只要求**记账 + 三条降级动作**，不要求调度器。
- 不得把 `MAX`（`DISCOVERY` 的额度）解释成"无限"——它只是没设上界，不是没有成本。

**待外部研究方决策：**

- 二级键选 `(surface, source)` 还是 `(source, surface)`？前者利于按表面对账，后者利于按源去重。
- 降级动作是**每源独立声明**还是**按表面统一**？
- 是否需要一个**总闸**（所有观测合计的上界），还是各源上界之和即总界？

### 方向 ②｜对象生命期账本（用 `can_tag_objects` + `OBJECT_FREE` 取代 6 处 `WeakReference`）

**定义：** 把"目标对象何时被回收"从**被动发现**升级为**确定性通知**。

**现状证据：**

- `src/main/java/dev/ronova/coremod/terminal/DurableTerminalWatchSet.java` — `WeakReference` 共 7 处出现，其中 **6 处是使用点**：
  `:92`、`:117`、`:285`、`:449`、`:459`（构造）+ `:434`（字段声明 `private WeakReference<Entity> reference`）；另 `:14` 是 import。
- 原生侧：`can_tag_objects` 命中 **0**、`OBJECT_FREE` 命中 **0**、`SetTag(` 命中 **0**、`GetTag(` 命中 **0**（`native/src/*.cpp`、`*.hpp`）
- 头文件侧两者**都存在**：`can_tag_objects` = `jvmti.h:670`，`can_generate_object_free_events` = `jvmti.h:702`
- 已声明的空位键：`RUNTIME_DYNAMIC_CODE_WATCH`（`StrengthOptionKey.java:60`，`restartRequired=true`）——但它不在上面的 6 个已发布键里

**缺口：** `WeakReference` 给你的是**"下次访问时才知道已经没了"**：

- 没有回收时刻通知——从对象被回收到你发现，中间是**不确定长度**的窗口；
- 没有顺序保证——多个目标在同一窗口内消失时，先后不可知；
- 发现时机取决于**访问模式**，而访问模式取决于外部输入——这不是可复现的语义。

对一个把"持久死亡权威"当核心的项目，**生命期靠轮询**是结构性弱点。`DurableTerminalWatchSet` 这个名字承诺的"durable"目前由弱引用轮询兜着。

**提议：**

1. 协商 `can_tag_objects` + `can_generate_object_free_events`（各自独立记错误，见 §3 协商链）。
2. 给已被 Ronova 追踪的目标对象打 tag，tag 值 = 该项目在账本中的稳定条目号（**不是**身份本身——身份仍然只有 `SubjectKey`，tag 只是账本索引，不得成为第二身份源）。
3. 在 `OBJECT_FREE` 回调里按 tag 结算：**此刻**该条目进入 terminal 判定，而不是下次访问时。
4. 回调里**只做最少的本地登记**（入队/置位），**不做**完整生命周期判定——回调线程与 safepoint 约束不允许重活。
5. `WeakReference` **保留**作为兜底（回调漏了、tag 没打上、协商失败时仍要能收敛），但**不再是发现路径的主干**。
6. tag 必须在释放时清理，否则是原生侧泄漏。

**前置依赖：** **方向 ①**（每个新增回调都要有成本行）。

**规则检查：**

- L0 — 不修改任何文件；不打 tag 到 Mod/Forge/依赖的对象上（只打给 Ronova 已追踪的目标）；不删除对方文件。**通过。**
- 需要注意的边界：tag 只作为**账本索引**，一旦它开始参与身份判定或权限判定，就变成了第二身份源——那是 P 层自洽性问题，会与"持久身份仍只有 `SubjectKey`"直接冲突。
- UX1 — 不涉及。

**验收标准：**

- 目标对象被回收后，账本在**回调返回前**（或明确声明的有界延迟内）观察到终态，而不是等到下次访问。
- 制造"协商失败"场景（不授予 `can_tag_objects`）：系统**回退到弱引用路径且行为不变**，并产生一条明确的诊断，而不是静默降级。
- 连续回收 N 个目标，账本条目**无泄漏**（tag 表不增长）。
- 与现有 `DurableTerminalWatchSet` 的 6 个使用点逐一对账，说明每处是被回调取代、还是保留为兜底。

**过度声称风险：**

- 不得写成"已实现确定性回收检测"。`OBJECT_FREE` 回调本身有 JVM 侧延迟与合并语义，是否严格"回收瞬间"取决于具体 VM——**必须先有实测再写结论**。
- 不得声称 tag 让身份更可靠。tag 不进身份。
- **头文件有 `can_generate_object_free_events` ≠ 运行时给。** 它属于偏门能力，很多配置下不可得。

**待外部研究方决策：**

- tag 的分配是全局单调，还是按 Realm 分段？（涉及 RealmId 语义）
- 回调里"最少登记"的具体边界：只置位，还是允许入队？入队是否可能无界增长？
- 若 `can_tag_objects` 可得但 `can_generate_object_free_events` 不可得（或反之），是**部分启用**还是**整体不启用**？（这是两个独立能力，必须分别声明）

### 方向 ③｜JIT 时机感知的重转换调度（`CompiledMethodLoad`）

**定义：** 用"方法何时被 JIT 编译"作为**重转换成本**的信号，把重转换安排在**便宜窗口**而不是最贵窗口。

**现状证据：**

- 原生侧：`COMPILED_METHOD_LOAD` 命中 **0**、`CompiledMethodLoad` 命中 **0**（`native/src/*.cpp`、`*.hpp`）
- 头文件侧存在：`can_generate_compiled_method_load_events` = `jvmti.h:697`
- 已声明的空位键：`RUNTIME_DYNAMIC_CODE_WATCH`（`StrengthOptionKey.java:60`）
- 现有一条 `jvmtiEventCallbacks` 表在 `native/src/ronova_native.cpp:828-833`（ClassFileLoadHook / ThreadEnd / 条件性 ClassPrepare）

**缺口：** 重转换一个**已被 JIT 编译**的方法会触发去优化（deopt）并丢弃编译产物；之后还要重新编译。重转换一个**解释执行/未编译**的方法几乎免费。

现在系统**不知道**这两种情况的区别，所以每次重转换都是盲赌。在极限档下重转换次数上升，这个盲赌的期望成本随之上升。

**提议：**

1. 协商 `can_generate_compiled_method_load_events`。
2. 维护一个**有界的**"已编译方法"视图（它天然会增长——必须有淘汰策略，且淘汰策略要写进契约）。
3. 重转换请求进入时，查该视图：已编译 → 可延后到声明的窗口；未编译 → 立即执行。
4. **延后不是取消**：必须有一个上界（时间或次数），到界强制执行，否则"延后"会变成"永不"。

**前置依赖：** **方向 ①**。同时受 §3 的一条硬约束管辖：`SetEventCallbacks` 会**替换整张回调表**，新增回调必须并入**共享装配点**，不得另开一条注册路径——`R66-CAPABILITY-WIRING-PLAN.md:265` 已记录此点。

**规则检查：** L0 — 不涉及。UX1 — 不涉及。P 层 — 新增调度维度，需与既有重转换路径的幂等键对齐，不得产生第二次转换语义。

**验收标准：**

- 能观测到"同一重转换请求，在已编译/未编译两种情形下走了不同路径"的证据。
- 延后上界被触发时，重转换**确实执行**（不是被丢掉）。
- "已编译方法"视图有明确上界，且达到上界时行为已声明（淘汰最旧 / 拒绝新增 / 压缩）。

**过度声称风险：**

- **`CompiledMethodLoad` 是通知，不是控制。** 它不让你"阻止 JIT"，只让你"知道 JIT 发生了"。任何"控制编译"的措辞都是错的。
- 不得声称省下了具体的毫秒数——**没有实测就没有数字**。
- 视图的陈旧性：方法可能已被回收/重定义，而视图不知道。必须声明陈旧容忍度。

**待外部研究方决策：**

- 延后上界用**时间**还是**次数**？（时间是外部可预期的，次数是与负载相关的）
- 已编译视图的规模上界取多少，依据是什么？
- 是否值得做？这条的**收益取决于重转换实际频率**——如果实测显示重转换很少发生，这条应当**降级或废弃**。请不要因为"技术上可行"就保留它。

### 方向 ④｜`ATTACK_TARGET_CLASS_LINEAGE` 的执行器

**定义：** 给一个**已在键表里、已在书里被引用、但没有执行器**的键补上真实执行路径。

**现状证据：**

- 键**存在**：`StrengthOptionKey.java:20` — `ATTACK_TARGET_CLASS_LINEAGE("attack.target_class_lineage", PlaneId.ATTACK, true)`
- 书里**已引用**三处（`docs/plans/MS-SKILLS-PLAN.md`）：
  - `:4483` — Registry 行，与 `ATTACK_REGISTRATION_SOURCE`、`ATTACK_LOGIC_SOURCE` 并列
  - `:5569` — M01 准确身份行，与 `source_trace`、`classloader` 并列
  - `:12626` — D10 行（"隐藏类/匿名类承载实体逻辑"），配套 `intercept.classloader`
- 全仓 Java 侧 `target_class_lineage|TARGET_CLASS_LINEAGE` 命中 **4**——与上面的键定义 + 书内引用量级相符，**没有独立执行器**

**缺口：** 这是"存在接线 ≠ 触达"的典型：键存在、书引用、但没有执行器消费它。按 §0.2 第 2 条闸，**当前状态不得声称该键已支持**。

**这条与 V1.1/V1.2 的"C11 已有本地路径"不同**：C11 的情况是本地通道**存在但故意不发布**；这条是**执行器不存在**。两者不能混为一谈，处置也不同（C11 补汇报，这条要建执行器）。

**提议：**

1. 明确该键的**执行范围**：它作用于哪一类目标？隐藏类/匿名类承载的实体逻辑（D10 行）是书里给的用例。
2. 建立 lineage 解析：从"目标对象"到"定义它的 Class / ClassLoader / 注册产物"的链路。
3. 明确**谁举证**：lineage 的每一跳由什么证据支撑，证据何时失效。
4. 明确**哪个实际执行器消费它**——没有这一项就不算接线。

**前置依赖：** 与 `intercept.classloader`（`StrengthOptionKey.java:29`，`restartRequired=true`）有语义邻接，需先确定二者的职责边界，避免同一能力有两个入口。

**规则检查：**

- L0 — 关键：lineage 解析是**只读**行为（读 Class/loader 关系），不修改任何文件。**通过。**
- 边界警告：这条离"针对特定目标"最近。lineage 是**结构关系**，不是"挑出某个玩家"。任何把它写成"找出对手的类"的用法都触碰"不针对"铁律。请在文档里把这条写死。
- UX1 — 不涉及。

**验收标准：**

- 存在一个真实执行器，能被观测到消费了该键。
- 给定一个由隐藏类/匿名类承载逻辑的目标，能产出 lineage 链路，且每一跳有证据来源。
- 证据失效时，结论**撤销**（与 `D75` 同构：历史 CLEARED 不得冒充当前完成，`MS-SKILLS-PLAN.md:4379`）。
- `ATTACK_TARGET_CLASS_LINEAGE` 从不与 `INTERCEPT_CLASSLOADER` 对同一事实给出两个互相矛盾的结论。

**过度声称风险：**

- 不得写成"可追踪任意目标类"。范围就是书里写的那类用例。
- 不得把"能读 Class 对象"等同于"能拿到 loader lineage"——loader 关系在隐藏类场景下有已知的解析困难，**必须实测**。

- 该键与 `INTERCEPT_CLASSLOADER` 是**分工**还是**合并**？（我倾向合并到一个入口，两个键名保留为不同粒度，但这需要你判断）
- lineage 需要解析到几跳为止？
- 与 D10 的绑定是硬绑定还是可选？

### 方向 ⑤｜证书到期闸 + 依赖集哈希（落在 `D75` 上）

**定义：** 让"证书还有效吗"成为一个**有依赖集哈希**的可判定问题，而不是一个时间戳比较。

**现状证据：**

- `D75`（`MS-SKILLS-PLAN.md:4379`）：
  > 当前证书的关键证据失效或目标再次漂移时，当前结果重新评估；历史 CLEARED 不得冒充当前完成
- `D75` 在 `docs/plans/INVARIANT-INDEX.md:150`、`docs/plans/VALIDATION-TRACEABILITY.md:69/105/110/188` 均有登记

**缺口：** `D75` 目前写的是**原则**（"证据失效则重新评估"），但没有写**怎么知道证据失效了**。原则不能被验收——能验收的是"依赖集变了"。

**提议：**

1. 每份证书携带**依赖集哈希**：把它所依赖的证据（版本、文件、配置、外部状态）归一成一个集合，对该集合取哈希。
2. 任何一次证书使用前，重算依赖集哈希并与证书内记录比对。
3. 不一致 → 证书视为失效 → 触发 `D75` 的重新评估，**且必须留下"因哪个依赖变化而失效"的记录**。
4. 与"目标再次漂移"合并到同一机制：漂移也是一种依赖集变化，不要做成两套。

**前置依赖：** 无硬依赖，可并行。但与方向 ① 共享"证据要可复核"的动机。

**规则检查：** L0 — 不涉及。UX1 — 不涉及。P 层 — 这是**给已有 `D75` 补可执行语义**，不是新增编号；需检查是否与既有 `PolicyRevision`/`ProjectionRevision` 语义重叠（若重叠，应复用而不是新造）。

**验收标准：**

- 构造"证书有效 → 篡改任一依赖 → 证书失效"的完整可复现轨迹。
- 失效时必须指出**是哪一个依赖**变了。
- 依赖集哈希计算本身稳定：同样的依赖集**必然**得到同样的哈希（顺序无关或顺序显式固定）。
- 不存在"证书有效但依赖已变"的窗口被静默放行。

**过度声称风险：**

- 不得声称"依赖集覆盖了所有可能失效原因"。它只覆盖**已枚举**的依赖。未枚举的变化不会触发失效——这一点必须写在文档里，不能留白。
- 哈希不是签名。它防的是**意外漂移**，不是**刻意伪造**。措辞不得含混。

**待外部研究方决策：**

- 依赖集哈希与 `PolicyRevision` 是同一条链还是两条？（我倾向复用，减少编号）
- 依赖集里放哪些项？需要一个**最小闭包**判断标准。
- 重算时机：每次使用前（贵、准）还是事件驱动（便宜、可能漏）？

### 方向 ⑥｜结算归属断言

**定义：** 对"这次结算由谁负责"做**显式断言**，使"没人负责"和"两个人都负责"都成为可检测的错误，而不是默认为正常。

**现状证据：**

- `TerminalLifecycle.java:44-64`：`:56` 是**可达**的委托（`runtime.terminalPlans().execute(...)`），`:61` 是**守卫**（防写入旧的无限制 writer）——注意：`:61` 不是死代码，它是活着的防护
- `TerminalActionPolicy.java:32-49` 的 `resolve()`，`:40-43` 第三处 `withCapability` 站点（本地作用域）
- 书里 `MS-SKILLS-PLAN.md:259` 给出"单一最终转换"的口径

**缺口：** "单一最终转换"目前靠**结构**保证（只有一条路径走到那里）。结构保证在**单线程、无异常**时成立；一旦插入新表面（方向 ⑦ 就是干这个的），"谁结算"就从一个结构事实变成一个**需要断言的运行时事实**。而断言现在不存在。

**提议：**

1. 每次结算前，断言**恰好一个**归属者被登记。
2. 归属者缺失 → **失败**（不是"没人做就算了"）。
3. 归属者重复 → **失败**（不是"先到先得"）。
4. 断言失败必须产生诊断，且**不得**让结算静默通过。

**前置依赖：** **方向 ⑦ 的硬前置**——多表面协调之前必须先能判断归属。

**规则检查：** L0 — 不涉及。UX1 — 不涉及。P 层 — 需要与 `RootCommandId` 幂等键对齐：重试时**归属者应当相同**（同一 command id 的恢复不得产生第二个归属者）。

**验收标准：**

- 构造"无归属者"场景 → 观测到失败 + 诊断。
- 构造"双归属者"场景 → 观测到失败 + 诊断。
- 正常路径不受影响（断言不产生误报）。
- `COMMIT_UNKNOWN` 恢复路径使用**原 command id** 重入时，归属者断言**不误判为重复**。

**过度声称风险：**

- 不得声称"这实现了分布式共识"——它只是**单体内的归属检查**。
- 不得声称"断言通过 = 结算正确"。它只保证归属唯一，不保证结果正确。

**待外部研究方决策：**

- 归属是**一个对象引用**、一个**枚举角色**、还是一个**带代次的槽位**？
- 断言抛异常还是返回错误码？（涉及与既有错误处理风格的一致性）

### 方向 ⑦｜跨表面预算分配器（落在 `D95` 上）

**定义：** 让多个表面同时作用于同一受保护结果时，预算由**一份计划**统一分配，而不是各表面各自扣。

**现状证据：**

- `D95`（`MS-SKILLS-PLAN.md:4429`）：
  > 多表面同时作用于同一 protected result 时，由一份 Root-approved CrossSurfaceOperationPlan 统一决定顺序、幂等键、lease、预算和 completion；表面之间不得互相调用形成循环修复、重复提交或结果振荡
- `D95` 在 `INVARIANT-INDEX.md:170`、`VALIDATION-TRACEABILITY.md:115/116/120/208` 均有登记
- 预算侧现状：`budget` 包内 `CrossSurface` 命中 **0** —— `D95` 要求的"统一决定预算"**在预算子系统里没有任何对应物**

**缺口：** `D95` 是一份**已写下的契约**，但它要求的能力**在实现里完全没有载体**。方向 ① 建的是"记账"，这条要的是"分配"。记账 ≠ 分配。

**提议：**

1. 在方向 ① 的二级键之上，引入**按受保护结果归集**的预算视图。
2. 多表面争用同一结果时，由 `CrossSurfaceOperationPlan` 分配额度，各表面**不得**独立扣减。
3. 顺序、幂等键、lease、completion 与预算**同源**——都来自那份计划，不得各表面自带。
4. 表面之间**禁止互相调用**（`D95` 已明确），实现上需要能检出这种调用（否则禁令无法验收）。

**前置依赖：** **方向 ①**（没有记账就没有可分配的量）+ **方向 ⑥**（没有归属断言就无法判断谁在争）。

**规则检查：** L0 — 不涉及。UX1 — 不涉及。P 层 — 这是 `D95` 的落地；需确认不与 `BudgetCategory` 现有 6 类冲突（建议**新增归集视图**而不是改 6 个类别本身）。

**验收标准：**

- 存在一份计划对象，能观测到多个表面从**它**取额度。
- 构造两表面争用场景 → 总额不超界，且**能指出谁被削减了多少**。
- 构造表面互调场景 → **被检出**（而不是仅仅写在文档里禁止）。
- 结果不振荡：同一输入重复执行产生同一分配。

**过度声称风险：**

- 不得声称"已实现全局最优分配"。它只保证**不超界、不互调、不振荡**。
- `D95` 的 "Root-approved" 需要与既有 Root Authority 对齐——**不要新造一个批准者**。这是 P 层自洽性的高危点。

**待外部研究方决策：**

- 分配算法用固定优先级还是按需协商？（固定优先级可预测，按需更省但难验收）
- 争用时是**削减**还是**排队**？
- 需要几个表面才能真正验证这条？两个够吗？

```
① 观测成本模型  ──┬─→ ② 生命期账本（新原生回调）

```

**建议批次：**

| 批次 | 内容 | 理由 |
|---|---|---|
| **1** | ① + ⑨ + ⑥ | ① 是根；⑨ 成本最低且立刻降低声称风险；⑥ 无强前置且是 ⑦ 的门 |
| **2** | ④ + ⑤ | 各自独立，规格清晰 |
| **3** | ⑦ | 依赖 ①⑥ 完成后才有意义 |
| **4** | ② + ③ | 都要新原生回调，等 ① 的账本+实测数据 |
| **研究** | ⑧ | 与实现批次解耦，可随时否掉 |

**明确建议 ③ 保留"废弃"出口**：它的价值完全取决于重转换的实际频率。若实测显示频率低，**应当废弃**，不要因为技术可行而保留。
