## 核心判断

它的存在维持主要依赖“静态对象保留 → 独立线程重复修复 → 多个世界索引重新发布 → 查询与渲染补入”，不能简化为 NBT 复制后调用实体工厂。旧实例可以一直存在，只是反复回到世界可见集合。因此，工厂拦截证据不能代替这类恢复链的处置证据。

## 保存路径的边界

`level/SSSaveData.java:12–34` 仅保存、加载一个 `someValue` 整数。对包内全部 Java 搜索 `SSSaveData`，命中仅在该类自身；没有找到实体恢复链调用该类的证据。

这不证明整个 Mod 完全没有持久化：实体常规序列化、游戏保存流程及动态代码仍可能参与。但该类不能作为“恢复记录已序列化、提交、独立读回并在重启后接续”的现成实现。7.17 的外部保存闭环仍需自行完成。

## 转化为通用验收场景

以下是新增的具体场景设计，不是已通过测试，也不是新增 Mod ID/类名黑名单。

1. **原对象重插**：静态 holder 保留原对象；删除世界记录后重复修复。生产观察必须发现来源，稳定窗口被重插撤销；无证据时明确未决。
2. **共享裸线程**：一条线程同时维护目标与无关对象，并忽略中断。准确处置目标来源和发布权限；无关对象继续工作，不停止共享线程。
3. **旧容器迟到发布**：复制容器后暂停，Root 清除/撤销资格，再允许发布。旧许可不能写入；其他条目和未知字段保留。
4. **旧对象跨世界接续**：同 UUID 新对象触发旧对象换 holder/世界重新挂接。不得把新对象清除当成旧链关闭；合法新资格不继承旧权限。
5. **查询与渲染分离**：世界原始索引为空，但自定义查询或客户端仍暴露静态对象。普通状态不得误报整链处置。
6. **隐藏定义与代码变更**：相同名字的不同定义类、运行中 observer 被改变、普通反射返回空。无法证明覆盖时撤销当前完成性，不继续沿用旧证明。

阶段归属：1–4 是阶段一已有来源、任务、最终写入与重插要求的具体化；5 的服务端观察属于阶段一，完整客户端验收留在阶段三；6 的必要证明失效处理属于阶段一，全面代码对抗留在阶段二。
