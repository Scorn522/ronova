## 解决的问题

r58 的资格 batch 主要靠请求的全局 DominionEpoch 拒绝过期提交，未把请求读取到的逐主体资格放入 canonical payload。r59 增加不可变的 `QualificationPreconditions`：Realm、政策配置 revision，以及精确覆盖全部目标的 SubjectKey/TargetEpoch/terminal 预期值。

- `qualify` 经现有 RootCommandBus → Gateway → LocalDominionStore → ShadowDurableRootStore 读取一个 acknowledged head；不写 Root、不改变请求的决策 epoch。
- 预期值排序、去重并检查 Realm，必须覆盖完整 batch；canonical hash 同时绑定这些值。带有预期值的旧请求不会在重试时刷新资格。
- Root 在同一 commit monitor 下检查预期值；任一主体、Realm 或政策版本不符，整批返回 REJECTED，不留下墓碑、资格、journal 或物理执行。
- 原有全局 epoch 和受保护 Owner 检查保留。新 committed receipt 必须包含预期资格各自精确推进一次后的结果，不能只给部分目标或跳号。
- JudgmentEngine 的批量及零目标路径、JudgmentExecutor 的单目标路径已显式接线。历史兼容入口保留原始命令语义，不在 commit 内偷偷替换 payload。
- NBT 把 schema-1 预期值放入现有 command journal 的版本化字段；解码验证类型、版本、完整目标、hash 和回执。缺失/篡改字段不能降级成无预期值的新命令。
- Root schema 5、command journal format 3、qualification extension 1、协议 9、Native DLL 不变。旧命令不补写预期值，不改变其原 canonical hash；r58 不支持回读已经写入新 guarded command 的存档，回退仍使用对应备份。
