## 1. 结论

7.16 的核心源码闭环已经建立：Java `DurableRootStore` 成为唯一权威 durable writer，裁决按动作级 `JudgmentBatch` 原子提交，客户端重试可用稳定 ingress command id 在目标发现前恢复 durable receipt，`COMMIT_UNKNOWN` 可按原命令恢复，有限终态 retry 被墓碑所有的永久 `TerminalWatchSet` 取代，强度策略具备稳定 key、持久化、revision、重启激活与真实状态分离。

## 2. 已实现

### 2.1 Durable Root cutover

- `ShadowDurableRootStore` schema 升至 3，并在 7.16 镜像晋升后成为 authoritative store。
- `LocalDominionStore` 只向 Java Durable Root 写入；旧 `DominionLedger` 仅接收 downgrade/recovery 镜像。
- 旧镜像写失败只增加诊断计数，不得 fence、撤销或覆盖 Root truth。
- 新增世界目录内的 `ronova/durable-root-v1.bin`：Root state 与 command journal 先编码为有界 NBT payload，再写入临时文件、`FileChannel.force(true)` 并要求原子替换；文件系统不支持原子替换时返回模糊提交，不降级为普通覆盖。
- 文件容器冻结 magic、format version、payload length 与 SHA-256；64 MiB 上限同时约束编码和读取。损坏、截断、checksum 不符、cutover 后文件缺失均 fail closed，不得静默退回 SavedData。
- command journal format 2 只保存命令、before/after epoch、commit index、状态与 payload hash；Root Snapshot 在权威图像中只保存一次，不再由每一条 journal row 重复嵌入。旧 format 1 row 仍可读取，并在下一次保存时迁移为紧凑格式。
- `SavedData#setDirty()` 现在只维护 downgrade mirror，不能单独证明 durable commit；只有权威文件写入成功后才允许返回 `COMMITTED`。
- malformed RealmId、Realm mismatch、state/policy hash drift 与非法 schema 均 fail closed。
- `CommitReceipt` 固定 command id、canonical payload hash、before/after epoch、commit index 与状态。

### 2.2 原子 JudgmentBatch

- 一个玩家动作只生成一个 `JudgmentBatch`、一个 command id、一个共享 decision epoch。
- 全部目标先纯准备，再在同一 Root transaction 写入；物理终结只在 committed receipt 后执行。
- 同一批内 Judgment、墓碑、Admission revision、TargetEpoch seam、撤销边界与 receipt 不分裂发布。
- 已授权的有序动作即使没有发现目标，也提交带稳定 command id 的 durable empty receipt；它不制造新 projection epoch，但重启后仍能幂等确认同一动作。
- 普通空批和无变化命令不制造新 projection epoch。

### 2.3 COMMIT_UNKNOWN / replay

- `BEFORE_APPLY` 与 `AFTER_APPLY_BEFORE_ACK` failpoint 可区分验证。
- Root 先尝试按原 command id + canonical payload hash 恢复；不得生成替代 command。
- 服务端 ingress command id 由 `RealmId + player UUID + client session id + sequence` 确定性派生；动作类型写入不可变 command domain 与 canonical payload。相同序号改发另一种动作只能触发 payload/domain 冲突，不能获得第二个 durable command。
- 协议升至 9：`OwnerState` 下发服务端 `RealmId`，`ActionRequest` 必须回传该 Realm。客户端断线时只保留尚未确认的 outbox；仅重连同一 Realm、同一玩家上下文才沿用原 session/sequence，世界或玩家上下文改变都会丢弃旧输入并创建新会话。
- 收到有序动作后，服务端先检查进程内会话回执，再按稳定 command id 查询 Durable Root；该查询发生在目标发现和新 Authority 执行之前。
- 已提交但未收到 ACK 的批次可在丢弃进程内存后，仅从权威文件恢复相同 receipt；恢复前若仍有未落盘图像，只能继续返回 `COMMIT_UNKNOWN`。
- 已提交批次恢复后只返回原结果，不重复广播裁决表现；Root projection 只在本进程尚未发布该 epoch 时补发一次。
- 未解决的 `COMMIT_UNKNOWN` 不写入内存会话 journal、不发送 ACK、不广播结果；客户端可继续用原 session/sequence 重试。
- 已提交批次恢复后只发布一次；提交前失败不得泄露部分目标。
- command id 与不同 payload 复用会被明确拒绝。

### 2.4 Durable TerminalWatch takeover

- 删除 `JudgmentEngine` 的有限 `RETRY_DELAYS` 生命周期语义。
- logical membership 由 durable tombstone 决定，不由尝试次数决定。
- HOT / WARM / COLD 三条调度 lane 只影响物理重断言频率，不影响终态资格。
- 实体引用为弱引用，维护受 `WorkBudget` 的计数/时间边界约束。
- Admission 发现同 UUID 或同 lineage 新 incarnation 时立即提升到 HOT lane。
- Root 已提交但进程在物理死亡/清除完成前崩溃时，TerminalWatch/Admission 会调用 committed completion 路径继续收敛；一次性死亡整合先争用 durable lifecycle receipt，重复恢复不会重复掉落或死亡副作用。
- 只有 committed `ClearTombstone` / `ClearTombstones` 才释放对应永久监视。

### 2.5 StrengthPolicy foundation

- 冻结 `StrengthProfile`：`COMPATIBLE`、`ENHANCED`、`EXTREME`、`CUSTOM`。
- 冻结 54 个 `StrengthOptionKey`：15 攻击、10 拦截、17 防护、12 运行时。
- 冻结六档 `MechanismLevel`：跟随预设、关闭、监控、保护若娜瓦、相关路径、全部严格。
- `StrengthPolicySnapshot` 分离 configured、active、supported ceiling、effective、evidence 与 activation。
- 所有策略变更作为一个 coherent profile 保存，当前 JVM 不做局部热切换；重启加载后整体激活。
- policy revision 与 canonical policy hash 持久化；损坏或篡改时 fence。
- `/ronova strength compatible|enhanced|extreme|custom` 提交预设。
- `/ronova strength status` 显示 revision、configured、active 与 pending restart。
- `/ronova status` 增加 Durable Root 与强度策略状态。
- `/ronova status` 同时报告 durable file 是否存在、是否仍 pending 以及最近一次持久化失败原因。

### 2.6 Versioned extension seam

- `VersionedExtensionId`、`VersionedExtensionEnvelope`、`VersionedExtensionCodec`、`VersionedExtensionRegistry`。
- envelope 有 1 MiB 上限、SHA-256 校验与 defensive copy。
- 预留 `TargetEpochExtension`、`WriteSinkExtension`、`CompletionContractExtension`。
- 7.16 只冻结 seam；完整 TargetEpoch propagation、Completion finality 与 WriteSink executor 属于 7.17/L6E。

## 5. r52 exact-artifact 出口门

在有 ForgeGradle 依赖和 JDK 17 的构建机执行：

```text
./gradlew clean build --no-daemon
```

必须确认：

1. `build/libs/ronova-0.2.0-alpha.7.16-r52.jar` 存在且已 reobf；
2. 41/41 分层 SelfTest PASS；
3. 成品不包含 `build-support/stub-sources` 的类；
4. JAR 无重复条目，Mixin/refmap、协议 9 五包 schema、资源与两个 DLL 完整；
5. 记录大小、条目数、SHA-256；
6. 用 r51 世界副本完成 migration → save → restart → policy pending/restart → judgment/clear 回归；
7. 对 `BEFORE_APPLY`、`AFTER_APPLY_BEFORE_ACK` 做实际进程终止恢复，并验证损坏/缺失 `durable-root-v1.bin` 会拒绝启动而非回退；
8. 在丢失 ACK 后重启服务端，用原 client session/sequence 重发同一动作；分别覆盖“目标仍存在”和“目标已不再可发现”，确认只返回原 durable receipt，不产生第二 epoch、第二掉落或第二视觉广播；
9. 在同一 Realm/玩家/session/sequence 下把动作从 PRIMARY、AREA、LOADED 任意改为另一种；进程内与重启恢复后都必须拒绝 payload/domain 冲突，不能发送成功 ACK 或生成第二条 durable command；
10. 完成 Windows Forge、Native/JVMTI/Agent 与 process-tree 验收后，才可冻结 7.16。
