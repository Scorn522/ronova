# Ronova 7.17 r55 — 死亡整合 claim 的模糊提交恢复

> 历史归档（2026-09-08 整理）：保留当时的设计、实现和验证口径，不代表当前源码状态。文中的“当前”“下一步”属于记录当时。
> 当前入口：[进度](../../CURRENT-PROGRESS.md) · [有效规划](../../plans/README.md)。

日期：2026-09-06。版本：`0.2.0-alpha.7.17-r55`。
依据：V2.6 §12.6、§15.7、§16.6 B 的副作用未知恢复约束。
本批修复现有生产死亡入口的 intent 恢复窗口，不宣称完成整个 B 批或通用 effect journal。

## 问题与行为

旧实现写入 lifecycle claim 后，如果持久化返回失败，会删除内存 claim 并清除 pending。
原子替换可能已经成功；丢失 ACK 不能证明磁盘上不存在该 claim。
同一 JVM 后续请求或另一物理对象因此可能再次获得死亡入口执行资格。

r55 先解析已有 Root 图像的持久化，再创建 claim；只有首次 intent 落盘成功才发放资格。
intent 写入不明时保留原记录、哈希与 pending，后续请求只恢复该 intent，永不重新发放资格。
这种保守恢复可能跳过一次尚未发生的死亡整合；对不可查询的第三方回调，不能猜测未执行再补做。
既有墓碑和可重复的终态维持继续沿原链执行。

`LifecycleClaimResult` 分开报告：

| 状态 | 含义 | 可进入死亡回调 |
|---|---|---|
| GRANTED | 首次 intent 已获持久化 ACK | 是，仅本次 prepare |
| ALREADY_CLAIMED_EFFECT_UNKNOWN | intent 已存在，物理效果完成性未知 | 否 |
| CLAIM_PERSISTENCE_UNKNOWN | Root/intent 持久化仍不明；可能尚无 claim | 否 |
| REJECTED | 非权威、fenced、无目标墓碑或无可恢复 claim | 否 |

旧 `claimLifecycleIntegration` 入口保留为薄适配器，只在 GRANTED 返回 receipt。
执行链仍为 TerminalLifecycle → DominionServerRuntime → LocalDominionStore → ShadowDurableRootStore。
恢复不会推进 Judgment epoch、command commit index 或生成新 canonical command。

`/ronova status` 新增 O(1) 的 `lifecycle_unverified_claims`。
此数值是当前保留的 claim 数，不是死亡成功数；结合现有 durable pending/failure 字段解释。

## 格式与迁移

Root schema 3、policy schema 3、网络协议 9 均不变。
`LifecycleIntegrationReceipt` 的字段、NBT 与 canonical hash 保持原样；旧 claim 继续阻止重复入口，不能升级成效果完成证明。
54 个高级键、14 个普通动作、预设与重启激活语义不变。

## 验证

四项聚焦任务已通过：DurableRootStore、StrengthPolicy、TerminalWatchSet、ProjectionWiring。
新增用例位于现有 DurableRootStoreSelfTest 中，测试注册数仍为 42。

- 实际临时文件：写入前失败、原子替换成功后 ACK 失败，区分实际磁盘状态。
- 失败期间持续保留 intent；继续写失败时保持 UNKNOWN；恢复写入成功后仍不授予执行。
- 丢弃内存并从真实文件重建后，同一 claim 不重发，历史哈希仍有效。
- Judgment 本身未持久化时不创建 effect intent；原命令恢复后才可首次申请。
- 16 个并发请求仅获得一次执行资格；已有/未知 claim 不因物理身份变化再次执行。
- fenced writer 拒绝恢复；effect 记录不推进 Judgment epoch/commit index。

这些是存储与执行许可层回归，没有在真实 Forge 中调用第三方死亡/掉落回调。
完整 build 与成品清单以 `BUILD-RESULT-r55.txt`、`build-r55.log` 为准。

## 尚未覆盖

本批只约束 public death entry 的原有 claim。`kill/discard/remove`、其他回调和跨表面步骤没有因此获得 exactly-once 保证。
旧 claim 仍按已有 judgment UUID/receipt 语义保存，没有冒充 V2.6 的通用稳定 effectKey、canonical SubjectKey、TargetEpoch 全链租约或 completion proof。
这些需与独立 executor 的语义授权、存储容量/恢复 reserve、查询与补偿合同一起继续实现。
Windows Forge、世界迁移、真实进程终止、多人、Native/GPU 验收仍未执行；X63–X65 不标为整体 PASS。
