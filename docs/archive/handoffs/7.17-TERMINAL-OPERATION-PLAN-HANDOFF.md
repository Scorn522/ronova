## Root 计划与执行

- 既有 Root/Store 从原 committed qualification receipt 生成 `TerminalOperationPlan`，绑定原 command/hash/index、SubjectKey、完整资格和物理 nonce、active/configured policy、Root-issued plan revision。
- planId 沿用 commandId，plan revision 来源于已确认 Root commit index；重规划可以改变计划版本，但不改变稳定 effectKey。读取和重建计划不提交第二次 Judgment，也不写第二份 Root 文件。
- 固定合同 `ronova:terminal-server/v1` 顺序为 admission fence → server presence → terminal lifecycle → network projection。前两步只维护 Ronova 自有登记，并检查后置状态；网络步只声明服务端投递，不声明客户端完成。
- 每步执行前复验 Root 计划；生命周期内部的重要调用/写入之间继续复验。回调中发生 clear、Owner/资格或政策变化时，剩余旧步骤停止；不继续发布旧 mark 或登记旧 watch。
- 同一 command/Subject 的同步反馈用 causality key 抑制重入；网络派发按计划版本有界去重。现场报告至多保留 32 条，并明确是否被 Root 接受，不把 executor 自报变成 Authority Truth。
- live plan 使用已接线资源 governor 的 16 KiB 估算 RECOVERY reservation，始终释放；资源不足时计划 FENCED，Root 裁决不被删除。

## 生命周期未知效果

r62 的持久 intent 只覆盖 public-death，kill/discard/remove 仍在外围。新绑定裁决现在把准备、效果清理、public death、kill/discard/remove 和相关原始状态回调放在一个 OPAQUE `ronova:terminal-lifecycle/v1` 步骤里。

- 先经同一 Root writer 持久化 intent 和原 attempt，再检查入口资格后调用整个步骤。
- 正常返回、部分返回或异常都不能证明任意第三方效果完成；记录仍为 EFFECT_UNKNOWN，计划整体不声明 completionSatisfied。
- 旧 public-death 与新 lifecycle bundle 是互斥兼容入口：同 command/Subject/TargetEpoch 已有旧记录或 claim 时，新名字不能生成第二次尝试；反方向同样拒绝。loader 也拒绝同一语义 slot 同时出现两类记录。
- 重规划、恢复和同一实体重复收敛只重新检查受控登记与投影，不重放未知的生命周期步骤。已经发生的未知效果在 clear 后仍保留。
- 首次 bundle 本身包含多个旧 API 调用，它不是“任意第三方全部副作用 exactly-once”的保证；其保证是获准 bundle 的一个尝试不被重试或换名重放。

## 兼容与剩余边界

Root 外层 schema 5、journal 3、effect schema 1、qualification 1/2、协议 9、Native DLL 保持不变。effect schema 中增加注册语义，r62 及更早版本不能回读已写入新 bundle 的世界；回退使用匹配备份。已有历史 hash、public-death 记录和 receipt 不改写。

新绑定实体的生产裁决与维护进入计划路径。尚未完成身份迁移的 legacy/unqualified 入口保留旧兼容边界，不能用本批验证代替它们的完整效果证明。

Root 接受步骤报告只表示它符合当前计划/资格和持久效果事实；没有客户端 completion receipt，也没有完成所有实际 WriteSink 的并发原子门。检查之间的并发 TOCTOU、第三方回调内部行为、QUERYABLE/IDEMPOTENT/COMPENSATABLE 恢复器仍是后续工程。通用 Surface registry 仍只登记观察端口，不因本计划直接升级成所有表面的 S3–S6。
